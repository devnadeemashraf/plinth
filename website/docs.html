Plinth Developer Documentation

Plinth is an enterprise-grade TypeScript backend platform designed around pure Hexagonal Architecture (Ports and Adapters). It provides the robust structural foundation needed to build high-scale, production-ready APIs with 100% code ownership and zero vendor lock-in.

Core Design Promise: Your business and domain logic never imports an HTTP framework, database driver, ORM, or cloud SDK. Infrastructure connects via strongly-typed port interfaces validated by shared contract tests.

Quick Start & CLI

The fastest way to scaffold a production-ready backend is using the Plinth CLI. It provisions a full monorepo with pre-configured ports, adapters, database migrations, and testing suites. 

# Scaffold a new backend project
npx @plinth/cli init my-backend

# Or using pnpm
pnpm create @plinth/app my-backend

# Navigate and start local development
cd my-backend
pnpm install
pnpm dev

The interactive scaffolding wizard prompts you to select your preferred drivers:

  • HTTP Engine: Fastify (ultra-high throughput) or Express (broad ecosystem compatibility)
  • Primary Database: PostgreSQL, SQLite (local single-binary), or MySQL
  • Cache Layer: Redis or In-Memory Cache
  • Queue Broker: Redis-backed BullMQ or Relational Database Queue

Using as NPM Packages

If you are integrating Plinth into an existing TypeScript project, you can install the standalone packages directly from the npm registry: 

# Install core framework primitives
pnpm add @plinth/core zod

# Install your chosen infrastructure adapters
pnpm add @plinth/adapter-fastify @plinth/adapter-postgres @plinth/adapter-redis

Hexagonal Principles

Hexagonal Architecture organizes software into three concentric layers:

  1. Domain & Business Layer: Pure TypeScript entity models, domain rules, calculation logic, and port definitions. Zero external library imports.
  2. Ports Layer: Contractual interfaces (e.g. DatabasePort, CachePort, HttpServerPort) that define what the application requires from the outside world.
  3. Adapters Layer: Concrete implementations that translate port calls to external protocols (e.g. SQL queries, HTTP responses, Redis commands).
// Example Port Definition: Clean, zero-infrastructure interface
export interface UserRepositoryPort {
  findById(id: string): Promise<User | null>;
  create(user: CreateUserInput): Promise<User>;
  updatePermissions(id: string, bitmask: bigint): Promise<void>;
}

Route Contracts & OpenAPI

Plinth uses type-safe route contracts to define the boundary between clients and your services. A route contract specifies path, method, headers, params, query parameters, request body, and response status codes using unified Zod schemas. 

import { defineRoute, z } from "@plinth/core";

export const getUserFeedRoute = defineRoute({
  method: "GET",
  path: "/api/v1/feed",
  summary: "Retrieve personalized user timeline",
  tags: ["Feed"],
  querySchema: z.object({
    limit: z.coerce.number().int().min(1).max(50).default(20),
    cursor: z.string().optional(),
  }),
  responseSchema: {
    200: z.object({
      posts: z.array(z.object({
        id: z.string().uuid(),
        authorName: z.string(),
        content: z.string(),
        likesCount: z.number().int(),
        createdAt: z.string(),
      })),
      nextCursor: z.string().nullable(),
    }),
  },
});

When mounted to any HTTP adapter (Fastify or Express), the contract automatically generates:

  • Strict request validation with standard 400 Bad Request error payloads
  • Full compile-time inference for request handlers and typed API clients
  • OpenAPI 3.1 JSON specification served at /openapi.json
  • Interactive API documentation served at /docs

O(1) Bitmask Authorization Engine

Traditional Role-Based Access Control (RBAC) relies on querying relational join tables (user_roles, role_permissions) on every request or storing massive arrays of permission strings in session tokens.

Plinth implements a high-performance $O(1)$ BigInt Bitmask Engine. Each permission is represented by an individual bit in a 64-bit integer: 

// Permissions defined as unique bit flags
export const PERMISSIONS = {
  NONE:            0n,
  POST_CREATE:     1n << 0n, // 1n
  POST_DELETE:     1n << 1n, // 2n
  COMMENT_CREATE:  1n << 2n, // 4n
  COMMENT_DELETE:  1n << 3n, // 8n
  USER_INVITE:     1n << 4n, // 16n
  MODERATE_FEED:   1n << 5n, // 32n
  ADMINISTRATOR:   1n << 63n, // Highest bit: Superadmin
} as const;

// Roles are bitwise combinations of individual permissions
export const ROLES = {
  MEMBER:    PERMISSIONS.POST_CREATE | PERMISSIONS.COMMENT_CREATE,
  MODERATOR: PERMISSIONS.POST_CREATE | PERMISSIONS.COMMENT_CREATE | PERMISSIONS.MODERATE_FEED,
  ADMIN:     PERMISSIONS.ADMINISTRATOR,
} as const;

// O(1) Sub-nanosecond verification function
export function hasPermission(userBitmask: bigint, required: bigint): boolean {
  if ((userBitmask & PERMISSIONS.ADMINISTRATOR) === PERMISSIONS.ADMINISTRATOR) {
    return true; // Superadmin bypass
  }
  return (userBitmask & required) === required;
}
Performance Benchmark: Bitmask evaluation executes in less than 0.5 nanoseconds with zero heap allocations, zero network requests, and zero database overhead.

Multi-Tenancy Isolation

Plinth guarantees tenant isolation through the TenantContext abstraction powered by Node.js AsyncLocalStorage. Every incoming HTTP request or queue job enters a scoped context: 

import { TenantContext } from "@plinth/core";

// Set during request authentication middleware
TenantContext.run({ tenantId: "tenant_abc123", userId: "usr_456" }, async () => {
  // Any downstream service or repository automatically inherits the context
  const currentTenant = TenantContext.getTenantId(); // "tenant_abc123"
  await postRepository.findAll(); // Automatically filtered by current tenant
});

Logging & PII Redaction

Security compliance requires that Personally Identifiable Information (PII) and sensitive secrets never leak into log aggregators, error trackers, or observability platforms.

Plinth features a dual-layer PII sanitization pipeline:

  • Layer 1 (Pre-flight Key Matching): Immediately redacts known sensitive fields (passwords, tokens, authorization headers, credit cards, SSNs) before object serialization.
  • Layer 2 (Deep Stream Regex Scanning): Scans serialized log strings for raw JWTs, bearer tokens, email patterns, and API keys that might be embedded in arbitrary messages or stack traces.
import { createLogger } from "@plinth/core";

const logger = createLogger({
  serviceName: "social-api",
  environment: "production",
});

logger.info({
  userId: "usr_123",
  email: "alex@example.com",
  apiKey: "plinth_live_9f8d7c6b5a4",
}, "User authenticated successfully");

// Emitted JSON log:
// {"userId":"usr_123","email":"[REDACTED_EMAIL]","apiKey":"[REDACTED_SECRET]","msg":"User authenticated successfully"}

Infrastructure Adapters

Plinth ships with production adapters designed to be wired together in your application's composition root (server.ts).

HTTP Server Adapters

Mount your business services to either Fastify or Express without modifying any route logic or validation schemas: 

import { FastifyHttpAdapter } from "@plinth/adapter-fastify";

const server = new FastifyHttpAdapter({
  port: 8080,
  host: "0.0.0.0",
  enableDocs: true, // Hosts Scalar API docs at /docs
});

// Register route contracts and business handlers
server.registerRoute(createPostRoute, async (req) => {
  const post = await socialService.createPost(req.body);
  return { status: 201, body: post };
});

await server.listen();

Database Adapters

All database adapters implement the DatabasePort interface, featuring parameterized query execution, nested transactions, and automatic connection health checks: 

import { PostgresDatabaseAdapter } from "@plinth/adapter-postgres";

const db = new PostgresDatabaseAdapter({
  connectionString: process.env["DATABASE_URL"],
  maxConnections: 20,
  idleTimeoutMs: 30000,
});

await db.connect();

// Transaction execution with automatic rollback on error
await db.transaction(async (trx) => {
  await trx.query("INSERT INTO accounts (id, balance) VALUES ($1, $2)", ["acc_1", 100]);
  await trx.query("INSERT INTO ledger (accountId, amount) VALUES ($1, $2)", ["acc_1", 100]);
});

Complete Example: Social Media Backend API

To demonstrate the power and cleanliness of Plinth in a practical real-world scenario, the repository includes a complete Social Media Feed Backend API located in examples/social-media-api/.

Feature Scope

  • User Profiles & Follow Graph: Follow and unfollow users with mutual connection tracking.
  • Post Publishing & Feeds: Create posts with character limits and tags; query chronologically ordered feeds.
  • Interactive Comments & Likes: Add comments to posts and toggle post likes with atomic counters.
  • Bitmask Role Permissions: Authors can delete their own posts; users with MODERATE_POSTS can delete any post.
  • Zero-Account SQLite Persistence: Runs anywhere instantly with no external database daemon.
  • OpenAPI & Scalar Documentation: Live interactive API browser served at /docs.

1. Defining the Port Interface

The domain layer defines the storage contract without knowing anything about SQLite or SQL: 

export interface SocialRepositoryPort {
  findUserById(id: string): Promise<SocialUser | null>;
  createPost(data: CreatePostData): Promise<SocialPost>;
  getPostById(id: string): Promise<SocialPost | null>;
  deletePost(id: string): Promise<boolean>;
  getTimeline(query: TimelineQuery): Promise<SocialPost[]>;
  createComment(data: CreateCommentData): Promise<SocialComment>;
  toggleLike(userId: string, postId: string): Promise<{ liked: boolean; totalLikes: number }>;
}

2. Service Layer with Bitmask Authorization

Business rules enforce fine-grained permissions: 

export class SocialService {
  #repo: SocialRepositoryPort;

  constructor(repo: SocialRepositoryPort) {
    this.#repo = repo;
  }

  async deletePost(callerId: string, postId: string): Promise<void> {
    const caller = await this.#repo.findUserById(callerId);
    if (!caller) throw new UnauthorizedError("User not found");

    const post = await this.#repo.getPostById(postId);
    if (!post) throw new NotFoundError("Post not found");

    // Allow if caller is the post author OR has MODERATE_POSTS permission
    const isAuthor = post.authorId === callerId;
    const canModerate = hasPermission(caller.permissions, PERMISSIONS.MODERATE_POSTS);

    if (!isAuthor && !canModerate) {
      throw new ForbiddenError("Insufficient permissions to delete this post");
    }

    await this.#repo.deletePost(postId);
  }
}

Quality Gates & Testing

Every change in a Plinth-based repository is validated against four non-negotiable automated quality gates: 

pnpm lint          # Biome strict linting and code formatting
pnpm typecheck     # Strict TypeScript build (--noEmit)
pnpm test:fitness  # Hexagonal architecture boundary verification
pnpm test:coverage # Vitest full test suite with >= 85% coverage threshold

Deployment & Health Probes

Plinth applications are cloud-native and container-ready out of the box. HTTP adapters automatically configure standard orchestrator probes:

  • GET /health/live: Liveness probe returning 200 OK if the process event loop is responsive.
  • GET /health/ready: Readiness probe verifying that database connection pools and cache layers are connected and ready to accept traffic.
