Docs / Introduction

Plinth Developer Documentation

Plinth is an enterprise-grade TypeScript backend platform designed around pure Hexagonal Architecture (Ports and Adapters). It gives solo developers and small engineering teams the hardened structural foundation required to ship high-scale APIs with 100% code ownership and zero vendor lock-in.

The Core Guarantee: Your domain models, business logic, and calculation services never touch an HTTP framework, database driver, ORM, or cloud SDK. Infrastructure connects through strongly-typed port interfaces validated by shared contract tests.

Most backend frameworks force you into a Faustian bargain: either you use a heavy, opinionated framework that locks your domain into proprietary decorators and runtime reflection magic, or you build from scratch and spend your first 2 to 3 weeks rewriting identical auth, multi-tenant isolation, rate limiting, and error handling boilerplate. Plinth solves this dilemma.

Quick Start & CLI

The fastest way to scaffold a project is using the interactive Plinth CLI. It provisions a standalone, production-ready monorepo with pre-configured ports, adapters, and automated fitness tests: 

# Initialize a new backend project interactively
pnpm create @plinth/app my-backend

# Or via npx
npx @plinth/cli init my-backend

# Navigate and launch local development
cd my-backend
pnpm install
pnpm dev

The wizard configures your backend interactively without forcing cloud dependencies:

  • HTTP Server: Fastify (ultra-high throughput) or Express (broad ecosystem compatibility)
  • Database Engine: SQLite (zero-daemon local dev & testing), PostgreSQL (with Row-Level Security), or MySQL
  • Cache Layer: In-Memory LRU or Redis
  • Queue Broker: Database Outbox Polling or Redis BullMQ
  • Storage & Email: Local filesystem / email catcher or cloud S3 / SMTP

Using Standalone NPM Packages

If you prefer to integrate Plinth primitives into an existing TypeScript project without the full monorepo scaffolding, you can install the standalone packages directly: 

# Install core framework primitives (zero runtime infrastructure dependencies)
pnpm add @plinth/core zod

# Install your chosen infrastructure adapters
pnpm add @plinth/adapter-http-fastify @plinth/adapter-db-postgres @plinth/adapter-cache-redis

Hexagonal Principles

Hexagonal Architecture (also known as Ports and Adapters) enforces strict dependency inversion. Software is divided into three distinct zones: 

+-------------------------------------------------------------------------+
|                  DRIVING ADAPTERS (Inbound Triggers)                    |
|       HTTP (Fastify / Express)  *  Cron Workers  *  CLI Commands        |
+------------------------------------+------------------------------------+
                                     | (Calls application)
                                     v
+-------------------------------------------------------------------------+
|                    APPLICATION & DOMAIN MODULES                         |
|                                                                         |
|   +-----------------------------------------------------------------+   |
|   |                      CORE DOMAIN KERNEL                         |   |
|   |   Entities  *  Bitmask RBAC  *  TenantContext  *  Redaction     |   |
|   +-----------------------------------------------------------------+   |
|                                                                         |
|   +-----------------------------------------------------------------+   |
|   |                         PORTS (Interfaces)                      |   |
|   |   DatabasePort  *  CachePort  *  QueuePort  *  StoragePort      |   |
|   +-----------------------------------------------------------------+   |
+------------------------------------+------------------------------------+
                                     | (Invokes ports)
                                     v
+-------------------------------------------------------------------------+
|                   DRIVEN ADAPTERS (Outbound Providers)                  |
|   PostgreSQL / SQLite  *  Redis / LRU  *  BullMQ  *  S3  *  SMTP        |
+-------------------------------------------------------------------------+

Why This Matters for Solo Developers

  • Zero Rewrites: Want to switch from SQLite to PostgreSQL? You change one adapter in your composition root. Zero lines of business logic or routes need modification.
  • Instant Unit Testing: Because domain services only depend on port interfaces, you can test them using simple in-memory stub implementations in sub-milliseconds without spinning up databases.
  • No Mocking Nightmares: You never mock ORM methods or framework request objects; you pass concrete stub adapters that satisfy the TypeScript interface.

Separation of Concerns

Plinth establishes non-negotiable boundaries between distinct concerns:

  1. Domain Entities: Immutable data shapes representing your business concepts (e.g. Note, User, Tenant).
  2. Ports: Pure TypeScript interfaces that define the capabilities required by the domain. They reside in src/ports/ or package exports.
  3. Services: Pure TypeScript classes orchestrating business operations, executing domain invariants, and validating permissions.
  4. Route Contracts: Single-source-of-truth Zod schemas defining HTTP method, path, parameter constraints, request body, and response status codes.
  5. Adapters: Concrete infrastructure implementations (Fastify, PostgreSQL, Redis) translating external protocols into domain port calls.
  6. Composition Root: The single application entrypoint (server.ts) that instantiates concrete adapters and injects them into domain services.

Architectural Fitness Scanner

Manual code reviews cannot catch every architectural leak. Plinth includes an automated Architectural Fitness Scanner (pnpm test:fitness) that inspects every file in your repository: 

# Run architectural fitness check across the codebase
pnpm test:fitness
Enforced Invariants:
  • Files in packages/core/src/ cannot import external HTTP libraries (Fastify, Express), database drivers (pg, mysql2, better-sqlite3), or ORMs.
  • Direct calls to process.env are prohibited outside src/config/.
  • Variable-depth relative path traversals (e.g. ../../../../src/...) are prohibited; canonical path aliases (@plinth/core, @/*) must be used.

Route Contracts & OpenAPI

Plinth replaces scattered controller routes with Route Contracts. A contract declares input validation, documentation tags, and response schemas using unified Zod schemas: 

import { defineRoute, type RouteContract } from "@plinth/core";
import { z } from "zod";

const noteResponseSchema = z.object({
  id: z.string(),
  title: z.string(),
  content: z.string(),
  isPinned: z.boolean(),
  tags: z.array(z.string()),
  createdAt: z.string(),
  updatedAt: z.string(),
});

export const createNoteRoute: RouteContract = defineRoute({
  method: "POST",
  path: "/api/v1/notes",
  summary: "Create a new note",
  tags: ["Notes"],
  bodySchema: z.object({
    title: z.string().min(1).max(200),
    content: z.string().max(20000).default(""),
    isPinned: z.boolean().default(false),
    tags: z.array(z.string().max(50)).default([]),
  }),
  responseSchemas: {
    201: noteResponseSchema,
  },
});

When registered with any HTTP adapter, the contract automatically provides:

  • Automated Request Validation: Invalid payloads immediately return RFC 9457 Problem Details with status 422 Unprocessable Content.
  • Compile-Time Type Inference: Handlers receive fully-typed input based on schema validation.
  • OpenAPI 3.1 Spec: Emitted automatically at GET /openapi.json.
  • Interactive Documentation UI: Powered by modern Scalar UI, served at GET /docs.

O(1) Bitmask Authorization Engine

Traditional Role-Based Access Control requires querying relational join tables (user_roles, role_permissions) on every HTTP request or stuffing large arrays of permission strings into JWTs.

Plinth implements a high-performance $O(1)$ BigInt Bitmask Engine. Each permission is a discrete bit in a 64-bit unsigned integer: 

// 1. Declare permission flags as BigInt bit shifts
export const PERMISSIONS = {
  NONE:            0n,
  NOTE_READ:       1n << 0n, // 1n
  NOTE_WRITE:      1n << 1n, // 2n
  NOTE_DELETE:     1n << 2n, // 4n
  NOTE_MODERATE:   1n << 3n, // 8n
  ADMINISTRATOR:   1n << 63n, // Highest bit: Superadmin
} as const;

// 2. Roles are bitwise OR unions of permission flags
export const ROLES = {
  VIEWER:    PERMISSIONS.NOTE_READ,
  EDITOR:    PERMISSIONS.NOTE_READ | PERMISSIONS.NOTE_WRITE,
  MODERATOR: PERMISSIONS.NOTE_READ | PERMISSIONS.NOTE_WRITE | PERMISSIONS.NOTE_DELETE | PERMISSIONS.NOTE_MODERATE,
  SUPERUSER: PERMISSIONS.ADMINISTRATOR,
} as const;

// 3. Sub-nanosecond O(1) evaluation function
export function hasPermission(userBitmask: bigint, requiredPermission: bigint): boolean {
  // Superadmin bit bypasses all granular checks
  if ((userBitmask & PERMISSIONS.ADMINISTRATOR) === PERMISSIONS.ADMINISTRATOR) {
    return true;
  }
  return (userBitmask & requiredPermission) === requiredPermission;
}
Performance Benchmark: Checking permissions via bitmask requires less than 0.5 nanoseconds with zero memory allocations, zero network roundtrips, and zero database queries on the request authorization path.

Multi-Tenancy Isolation

Multi-tenancy bugs are among the most dangerous vulnerabilities in software, often causing catastrophic cross-customer data leaks. Plinth eliminates manual tenant ID plumbing using TenantContext backed by Node.js AsyncLocalStorage. 

import { TenantContext } from "@plinth/core";

// Authenticated middleware sets the context for the asynchronous execution chain
TenantContext.run({ tenantId: "tenant_corp_01", userId: "usr_alex" }, async () => {
  // Downstream services automatically access tenant context without parameter passing
  const currentTenant = TenantContext.getTenantId(); // "tenant_corp_01"
  
  // Database adapters automatically inject tenant scope into queries
  await noteRepository.findMany(); 
});

Dual-Layer PII Redaction

Plinth protects sensitive data through a comprehensive dual-layer sanitization pipeline:

  1. Layer 1 (Pre-Flight Property Match): Before an object is serialized, properties matching sensitive keys (password, token, apiKey, secret, authorization, creditCard) are replaced with redacted markers.
  2. Layer 2 (Deep Stream Regex Sanitization): The output stream is scanned with high-performance regular expressions to catch raw JWTs, bearer tokens, and emails that may be embedded in freeform log messages or stack traces.
import { createLogger } from "@plinth/core";

const logger = createLogger({
  serviceName: "notes-api",
  environment: "production",
});

logger.info(
  { user: "alex", apiKey: "sec_live_9f8d7c6b5a4", email: "alex@example.com" },
  "User created a new note"
);

// Emitted Log:
// {"user":"alex","apiKey":"[REDACTED_SECRET]","email":"[REDACTED_EMAIL]","msg":"User created a new note"}

Crypto & Envelope Encryption

Plinth provides battle-tested cryptographic primitives out of the box:

  • AES-256-GCM Envelope Encryption: Encrypt sensitive configuration values and secrets at rest using authenticated encryption with derived data keys.
  • Memory-Hard Password Hashing: Powered by Argon2id with strict OWASP parameters (19 MiB memory, 2 iterations, 1 parallelism).
  • Pure Ed25519 JWTs: High-performance, quantum-resistant asymmetric digital signatures for stateless bearer tokens without OpenSSL overhead.
  • RFC 6238 TOTP: Two-Factor Authentication engine with timing-safe verification and drift tolerance.

Swappable Infrastructure Adapters

Plinth ships with production adapters designed to be wired together in your application's composition root (server.ts). Every adapter implements a strict Port interface.

HTTP Server Adapters

Switch between Fastify and Express without changing any business handlers: 

// Using Fastify (default for high throughput)
import { FastifyHttpAdapter } from "@plinth/adapter-http-fastify";
const http = new FastifyHttpAdapter({ port: 3000 });

// Or using Express (for legacy ecosystem compatibility)
import { ExpressHttpAdapter } from "@plinth/adapter-http-express";
const http = new ExpressHttpAdapter({ port: 3000 });

Database Adapters

All database adapters satisfy the DatabasePort interface:

  • @plinth/adapter-db-sqlite: Zero-daemon synchronous SQLite with WAL mode. Ideal for local dev, offline work, and CI pipelines.
  • @plinth/adapter-db-postgres: Full PostgreSQL client with connection pooling, transactions, and Row-Level Security (RLS).
  • @plinth/adapter-db-mysql: MySQL 2 adapter with promise pool and transaction support.

Cache & Queue Adapters

  • Cache: Choose between bounded in-memory LRU cache (@plinth/adapter-cache-memory) or distributed Redis (@plinth/adapter-cache-redis). Includes a built-in CacheCircuitBreaker that fails open if the cache cluster degrades.
  • Queue: Choose between a relational database outbox polling worker (@plinth/adapter-queue-db) or Redis BullMQ (@plinth/adapter-queue-bullmq).

Storage & Email Adapters

  • Object Storage: Local disk storage (@plinth/adapter-storage-local) or S3-compatible cloud storage (@plinth/adapter-storage-s3) with offline SigV4 pre-signed upload URLs.
  • Email: Local in-memory email capture (@plinth/adapter-email-stub) for development or SMTP transport (@plinth/adapter-email-smtp) with TLS verification for production.

Billing & Payments

Clean payment ports handling raw body HMAC signature verification, integer minor units (zero floating-point math), and idempotency deduplication.

Notes API Tutorial: Building from Scratch

This step-by-step walkthrough shows you how to build a clean, production-grade Notes API from scratch using Plinth. The complete working code is available in examples/notes-api/.

Step 1: Define Entities & Repository Port

Start with the domain. Define your data entity and the repository port as a pure TypeScript interface in src/domain/: 

// src/domain/types.ts
export interface Note {
  id: string;
  title: string;
  content: string;
  isPinned: boolean;
  tags: string[];
  createdAt: string;
  updatedAt: string;
}

export interface CreateNoteInput {
  title: string;
  content: string;
  isPinned?: boolean | undefined;
  tags?: string[] | undefined;
}

export interface UpdateNoteInput {
  title?: string | undefined;
  content?: string | undefined;
  isPinned?: boolean | undefined;
  tags?: string[] | undefined;
}

export interface ListNotesQuery {
  search?: string | undefined;
  isPinned?: boolean | undefined;
  limit?: number | undefined;
  offset?: number | undefined;
}

export interface ListNotesResult {
  notes: Note[];
  total: number;
}

Now define the secondary port interface in src/domain/repository.ts:

// src/domain/repository.ts
import type { CreateNoteInput, ListNotesQuery, ListNotesResult, Note, UpdateNoteInput } from "./types.js";

export interface NotesRepositoryPort {
  create(input: CreateNoteInput): Promise<Note>;
  findById(id: string): Promise<Note | null>;
  findMany(query: ListNotesQuery): Promise<ListNotesResult>;
  update(id: string, input: UpdateNoteInput): Promise<Note | null>;
  delete(id: string): Promise<boolean>;
  count(): Promise<number>;
}

Step 2: Implement the Service Layer

Implement business rules and error handling in src/services/notes-service.ts: 

// src/services/notes-service.ts
import { BadRequestError, NotFoundError } from "@plinth/core";
import type { NotesRepositoryPort } from "../domain/repository.js";
import type { CreateNoteInput, ListNotesQuery, ListNotesResult, Note, UpdateNoteInput } from "../domain/types.js";

export class NotesService {
  readonly #repo: NotesRepositoryPort;

  constructor(repo: NotesRepositoryPort) {
    this.#repo = repo;
  }

  async createNote(input: CreateNoteInput): Promise<Note> {
    const title = input.title.trim();
    if (!title) throw new BadRequestError("Note title cannot be blank");
    return this.#repo.create({ ...input, title });
  }

  async getNote(id: string): Promise<Note> {
    const note = await this.#repo.findById(id);
    if (!note) throw new NotFoundError(`Note with id '${id}' not found`);
    return note;
  }

  async listNotes(query: ListNotesQuery): Promise<ListNotesResult> {
    return this.#repo.findMany(query);
  }

  async updateNote(id: string, input: UpdateNoteInput): Promise<Note> {
    if (input.title !== undefined && !input.title.trim()) {
      throw new BadRequestError("Note title cannot be blank");
    }
    const updated = await this.#repo.update(id, input);
    if (!updated) throw new NotFoundError(`Note with id '${id}' not found`);
    return updated;
  }

  async deleteNote(id: string): Promise<void> {
    const deleted = await this.#repo.delete(id);
    if (!deleted) throw new NotFoundError(`Note with id '${id}' not found`);
  }
}

Step 3: Declare Route Contracts

In src/contracts/notes-routes.ts, declare type-safe Zod contracts for your endpoints: 

// src/contracts/notes-routes.ts
import { defineRoute, type RouteContract } from "@plinth/core";
import { z } from "zod";

const noteSchema = z.object({
  id: z.string(),
  title: z.string(),
  content: z.string(),
  isPinned: z.boolean(),
  tags: z.array(z.string()),
  createdAt: z.string(),
  updatedAt: z.string(),
});

export const createNoteRoute: RouteContract = defineRoute({
  method: "POST",
  path: "/api/v1/notes",
  summary: "Create a new note",
  tags: ["Notes"],
  bodySchema: z.object({
    title: z.string().min(1).max(200),
    content: z.string().max(20000).default(""),
    isPinned: z.boolean().default(false),
    tags: z.array(z.string()).default([]),
  }),
  responseSchemas: { 201: noteSchema },
});

export const listNotesRoute: RouteContract = defineRoute({
  method: "GET",
  path: "/api/v1/notes",
  summary: "List notes with pagination and search",
  tags: ["Notes"],
  querySchema: z.object({
    search: z.string().optional(),
    isPinned: z.enum(["true", "false"]).optional(),
    limit: z.coerce.number().int().min(1).max(100).default(20),
    offset: z.coerce.number().int().min(0).default(0),
  }),
  responseSchemas: {
    200: z.object({ notes: z.array(noteSchema), total: z.number().int() }),
  },
});

Step 4: Wire the Composition Root

Connect everything together in src/app.ts: 

// src/app.ts
import { FastifyHttpAdapter } from "@plinth/adapter-http-fastify";
import { createNoteRoute, listNotesRoute } from "./contracts/notes-routes.js";
import { StubNotesRepository } from "./infrastructure/stub-notes-repository.js";
import { NotesService } from "./services/notes-service.js";

export function buildNotesApp() {
  const repo = new StubNotesRepository();
  const service = new NotesService(repo);
  const http = new FastifyHttpAdapter({ port: 3000, enableDocs: true });

  http.registerRoute(createNoteRoute, async (req) => {
    const note = await service.createNote(req.body);
    return { statusCode: 201, body: note };
  });

  http.registerRoute(listNotesRoute, async (req) => {
    const result = await service.listNotes(req.query);
    return { statusCode: 200, body: result };
  });

  return { http, service, repo };
}

pnpm --filter @plinth/example-notes-api test
# ✓ 16/16 tests passing across happy path, validation, and error handling

Extending Plinth

As your application grows, you will add new vertical business modules and custom infrastructure adapters. Plinth provides strict patterns to ensure modularity.

Adding a Vertical Feature Module

When adding a new business domain (e.g. invoices, projects, subscriptions):

  1. Create packages/modules/<feature>/src/domain/: Define entities and repository port interfaces.
  2. Create packages/modules/<feature>/src/services/: Implement business rules with standard error classes.
  3. Create packages/modules/<feature>/src/contracts/: Define Zod route contracts.
  4. Wire the module into your composition root in apps/api/src/app.ts.

Adding a Custom Adapter

Need to connect to an external service (e.g. a specialized search engine, a legacy payment gateway, or proprietary queue)?

  1. Define the Port interface in packages/core/src/ports/.
  2. Create your adapter package in packages/adapters/<category>/<name>/.
  3. Implement the port methods in a clean class.
  4. Write black-box contract tests to verify drop-in parity.

Writing Contract Tests

Plinth uses shared contract test suites located in packages/contract-tests. A contract test runs against any adapter implementation to verify that it satisfies every invariant: 

import { runDatabaseContractTests } from "@plinth/contract-tests";
import { MyCustomDatabaseAdapter } from "./my-adapter.js";

// Validates connection, query parameter binding, transactions, rollbacks, and ping
runDatabaseContractTests("MyCustomDatabaseAdapter", () => new MyCustomDatabaseAdapter());

Production Readiness

Plinth applications are designed for modern containerized cloud deployments:

Health Probes

  • GET /health/live: Liveness probe verifying that the event loop is responsive.
  • GET /health/ready: Readiness probe verifying that database pools and cache clusters are active.

Graceful Shutdown

Plinth captures process signals (SIGTERM, SIGINT), stops accepting new requests, drains active HTTP connections, and closes database and cache pools safely with a configurable grace period.

Automated Quality Gates

Every commit in a Plinth monorepo is validated by four non-negotiable gates:

pnpm lint          # Biome strict linting across all files
pnpm typecheck     # TypeScript 7.0 composite project build (tsc --build)
pnpm test:fitness  # Hexagonal architecture boundary validation
pnpm test:coverage # Vitest full test suite (>= 85% coverage threshold)
